# 家族間アカウント管理アプリ「PoohMa」要件定義書

**プロジェクト名:** PoohMa (プーマ)
**バージョン:** 2.0.1
**最終更新日:** 2026/09/09

## 0. 本書について

### 0.1 目的

本書は、家族間アカウント管理アプリ「PoohMa」プロジェクトについての要件をまとめたものである。
提供機能の全体像・画面別の体系的カタログは [機能一覧 (features.md)](./features.md) を参照のこと。

### 0.2 対象読者

- プロダクトオーナー
- 新規参画エンジニア
- 本サービスの仕様把握を必要とする関係者

### 0.3 注意事項

- コードと矛盾する外部ドキュメントが存在する場合は、実装（コード）を正とする。

## 1. サービス概要

### 1.1 サービス名

PoohMa

#### 1.1.1 読み方

プーマ

### 1.2 コンセプト

「実際のパスワードを1文字もサーバーに預けない」ことを最大の特徴とする、家族専用のアカウント情報共有サービス。
パスワードそのものではなく、家族にしか分からない「パスワードのヒント」を暗号化して共有する。

### 1.3 ターゲットユーザー

- 動画配信サービス・Wi-Fi・各種サブスクリプション等のアカウントを家族で共有している世帯
- 親子・祖父母を含む、ITリテラシーに差がある家族構成
- 「パスワードを教え合うことへの心理的抵抗」「メモの紛失リスク」を課題としているユーザー

### 1.4 提供価値（バリュープロポジション）

以下の3点を中核的な価値提案として設計する。

1. **セキュリティ** ：サーバーに保存されるのは本人が決めた「ヒント」のみ。実パスワードは保存せず、ヒント自体も暗号化され、閲覧には家族パスコードが必要。
2. **かんたん共有** ：レコード作成・共有範囲の指定がボタン一つで完結する直感的な操作性。
3. **自由（ロックインしない）** ：登録した全データをいつでもCSVとしてエクスポートし、退会できる。

## 2. 用語定義

| 用語                       | 定義                                                                                |
| ------------------------ | --------------------------------------------------------------------------------- |
| 家族グループ（Family）           | サービス利用の前提単位。ユーザーは必ずいずれか1つの家族グループに所属する（未所属時は機能利用不可）。                               |
| マスターキー（Master Key）       | 家族グループ単位で1つ生成される家族共用の暗号鍵。家族が知る「家族パスコード」から導出した鍵でラップされてサーバーに保存される。                  |
| DEK（Data Encryption Key） | 認証情報（credential）1件ごとに生成される暗号鍵。マスターキーでラップされて保存され、パスワードヒント本体の暗号化に使われる（エンベロープ暗号化方式）。 |
| 家族パスコード                  | 家族メンバー各自が入力する、マスターキーのロック解除用の合言葉（10文字以上72文字以下、強度スコア2以上）。サーバーには保存されない。                              |
| サービスレコード（Service Record） | 1つのWebサービス・アカウントに対応する登録単位（タイトル、URL、認証情報群、タグ等を含む）。                                 |
| 認証情報（Credential）         | サービスレコード内の、ログインIDとパスワードヒントの組。1レコードに複数保持できる。                                       |
| 所有モデル（Ownership / ACL） | サービスレコードの所有種別。 `user` （登録者本人のみ閲覧可）と `family` （家族全員で閲覧可、管理者が共有解除・削除権限を保持）のDrive型所有権モデル。 |
| 参加申請（Join Request）       | 招待コードを用いて他の家族グループへの参加を申し込む処理。ステータスは pending / approved / rejected。                |
| 家族移行（Family Migration）   | ユーザーが所属する家族グループを変更（新規作成 or 他家族への参加）する処理。既存の暗号化データを新しいマスターキーで再暗号化する一連のトランザクション。ステータスはPREPARED / COMPLETED / EXPIRED / ABORTEDで管理される。    |
| OGP情報                    | 登録URLから自動取得するタイトル・画像・説明文（Open Graph Protocol）。                                    |
| ふりがな（読み仮名）               | サービス名から自動生成される読み仮名。五十音インデックス表示に利用。                                                |

## 3. 前提条件・ビジネス制約

- 利用には「家族グループ」の作成または参加が必須であり、未所属のユーザーは家族管理画面以外にアクセスできない。
- ログイン手段はGoogleアカウントのみを提供する（他のSNS/メールパスワード認証は提供予定なし）。
- サービスの設計思想として、実際のパスワードそのものを保存する機能を意図的に提供しない（「ヒント」の保存に限定する案内）。
- パスワードヒントのみをエンドツーエンド暗号化（E2EE）し、暗号化・復号処理はすべてブラウザ（クライアント）側で完結させる。サーバーへは暗号化済みヒントのみを送信する。サービス名・URL・メモ・タグ・ログインIDなどのメタデータはE2EE対象外であり、平文でサーバーに保存される。

## 4. ユーザー種別

| 種別             | 説明                                                                |
| -------------- | ----------------------------------------------------------------- |
| 未登録訪問者         | ログイン前の公開ページ（LP、使い方、FAQ、規約等）の閲覧のみ可能。                               |
| 登録済み・家族未所属ユーザー | Googleログイン済みだが家族グループに未所属。家族の作成・参加申請のみ可能。ダッシュボードなどにはアクセス不可。        |
| 家族メンバー         | 家族グループに所属し、全機能を利用可能。 |

## 5. 機能要件

### 5.1 認証・ユーザー管理

| ID         | 要件                                                                                                                                                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-AUTH-01 | Googleアカウントによるサインアップ／ログイン（iOSでのUXを加味し、Firebase Authenticationのリダイレクト方式）を提供する。                                                                                                                                         |
| FR-AUTH-02 | Firebase Authentication（IndexedDB + LocalStorage永続化）を長期ログイン状態の本体（Single Source of Truth）とし、数ヶ月単位でログインを維持する。サーバー側では補助セッションとしてhttpOnlyセッションCookie（14日間有効）を発行し、日常的な利用やトークン更新時に自動ローリング延長する。セッションCookieの期限切れのみを理由に未認証として扱ってはならない。 |
| FR-AUTH-03 | 初回・再ログイン時にユーザー情報（表示名・メールアドレス・プロフィール画像URL）をバックエンドDBへ同期する。メールアドレスの確認が完了していない（emailVerifiedがfalse）ユーザーの同期リクエストは拒否する。別FirebaseID・同一メールアドレスの既存ユーザーが存在する場合は、FirebaseIDの変更とみなし、そのユーザーの過去データ（レコード・参加申請 `joinRequests`・移行データ `familyMigrations`）を新しい認証IDへ引き継ぐ。表示名は `FR-AUTH-05` と競合するため、更新を行わない。 |
| FR-AUTH-04 | ログアウト機能を提供する（Firebaseサインアウト＋サーバー側リフレッシュトークン即時失効 `revokeRefreshTokens`＋セッションCookie失効＋クライアント側ログアウトフラグによるSPA遷移時の再認証防止＋ローカルキャッシュ破棄）。                                                                                                                                                               |
| FR-AUTH-05 | 表示名を設定画面から変更できる。                                                                                                                                                                                                      |
| FR-AUTH-06 | アカウント削除（退会）機能を提供する。退会時は本人が所有する全サービスレコードを、家族共有の有無に関わらず削除し、家族グループの最後の1人であった場合は家族グループ自体も削除する。                                                                                                                            |
| FR-AUTH-07 | セッションCookieが一時的に失効した場合でも、クライアント側Firebase Authの永続セッションから自動でCookieを再同期・復元する。両セッションが完全に失効した場合に限り、入力内容を保持したまま再ログインを促し、再ログイン成功後に自動で保存処理を再開する。                                                                                                                                   |
| FR-AUTH-08 | 1つのログイン認証（Firebase Auth）に対して複数のPoohMaアカウント（用途別・家族別）を作成・保持できる機能を提供する。                                                                                                                                           |
| FR-AUTH-09 | ヘッダーやメニューからアクティブなPoohMaアカウントを即時切り替えできる機能を提供する。切り替え時は、直ちに旧アカウントのMasterKeyを揮発性メモリから破棄し、ローカルキャッシュをクリアして新アカウントの再パスコードロック状態へ遷移する。                                                                  |
| FR-AUTH-10 | 複数アカウント所持時は、設定画面から「現在のアカウントのみ削除」または「PoohMa全体からの退会（Firebaseアカウント削除）」を選択して実行できる。                                                                                                                    |

### 5.2 家族グループ管理

| ID        | 要件                                                                                                                                                    |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-FAM-01 | 家族グループを新規作成できる（家族名の入力、パスコード10文字以上72文字以下かつ強度スコア2以上（NFR-SEC-13）の強度メーター付きバリデーション＋確認入力の一致チェック）。作成と同時にマスターキーを生成し、パスコード由来の鍵でラップして保存する。                                                            |
| FR-FAM-02 | 招待コード（有効期限付き、家族メンバーがその都度発行）・招待URL・QRコードの提示により、他ユーザーを家族グループへ招待できる。QRコードは画像として保存・共有（Web Share API対応）できる。                                                                |
| FR-FAM-03 | 招待コードを持つユーザーは参加申請を送信できる。既存メンバーのいずれかが申請を承認／却下する。                                                                                                       |
| FR-FAM-04 | 参加申請は送信者側からキャンセルでき、却下された申請は本人が削除（見送りの確認）した上で再申請できる。同時に保持できる保留中の申請は1件までとする。                                                                            |
| FR-FAM-05 | 現在所属する家族グループのメンバー一覧（表示名・メールアドレス）を表示できる。                                                                                                               |
| FR-FAM-06 | 所属家族グループを変更できる（新規家族作成 or 他家族への参加）。変更時、既存の暗号化済みパスワードヒントをクライアント側で新しいマスターキーに向けて再暗号化した上でサーバーへ送信し、レコードの所属家族を一括で付け替える。                                      |
| FR-FAM-07 | 家族移行処理は「準備（PREPARED）」状態を経て「確定（COMPLETED）」される2フェーズ方式とし、確定時にレコード一覧の照合（楽観的ロック）を行って移行中の更新競合を防止する。準備状態は作成から30分で自動失効（EXPIRED）する。ユーザーが移行前にキャンセルした場合はABORTEDとする。失効・中断した移行先の空家族グループ（メンバー0・レコード0）は自動削除する。 |
| FR-FAM-08 | 家族グループに未所属のユーザーは、家族管理画面以外の全ページで家族管理画面へ強制的にリダイレクトされる。                                                                                                  |
| FR-FAM-09 | 現在所属する家族グループのメンバー一覧から特定のメンバーを削除（キック）することができる。この場合、当該ユーザーは即時で強制的に家族変更を要求される。キック時、旧家族マスターキーはExport Vault（有効期限30日）へ一時退避され、被キックユーザーは旧パスコードを用いて個人所有レコード（ownerType: "user"）のみを新しい家族グループへ持ち出すことができる。家族共有レコード（ownerType: "family"）は家族側に残る。キック実行者には家族パスコードのローテーション（FR-FAM-10）を推奨案内する。 |
| FR-FAM-10 | 家族グループを変更せずにパスコードのみを変更（ローテーション）できる機能を提供する。実行時は、展開済みのマスターキーを新パスコード由来鍵で再wrapする（DEKおよびパスワードヒント本体は再暗号化不要。マスターキーのラップ鍵のみを変更するため、O(1)で完了する軽量操作）。 |
| FR-FAM-11 | 招待コードは有効期限（1時間/1日/7日[デフォルト]/30日から選択、サーバー側で最小15分・最大30日にクランプ）を設定して発行し、家族メンバーはいつでも手動で無効化できる。期限切れ・無効化済みコードでの参加申請は拒否する。定期クリーンアップにより30日以上前の失効・期限切れレコードは自動削除される。 |
| FR-FAM-12 | 家族グループ内に「ファミリー管理者（admin）」と「メンバー（viewer）」の非対称ロールを導入する。家族新規作成者は管理者となり、新規参加者は原則としてメンバー（viewer）ロールとなる。ファミリー管理者は他メンバーのロール昇格・降格、メンバー除名（キック）を行える。家族グループ内には最低1名の管理者が常時存在しなければならず、最後の管理者の降格・除名は禁止する。 |

### 5.4 暗号化・パスコードロック

| ID          | 要件                                                                                                                                                                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-CRYPT-01 | 家族グループごとに1つのマスターキーを生成し、家族パスコードから導出した鍵で暗号化（ラップ）してサーバーに保存する。                                                                                                                                                                                                                        |
| FR-CRYPT-02 | パスワードヒントごとに個別のDEK（データ暗号鍵）を生成し、マスターキーでラップして保存する（封筒暗号化）。パスワードヒント本体はDEKで暗号化する。                                                                                                                                                                                                       |
| FR-CRYPT-03 | アプリの起動直後および所属家族の切替直後は暗号鍵が未展開の「ロック状態」であり、パスワードヒントの登録・閲覧・編集・エクスポート操作の際にパスコード入力ダイアログを表示してロックを解除する。                                                                                                                                                                                   |
| FR-CRYPT-04 | 入力されたパスコードが誤っている場合はエラーメッセージを表示し、再入力できる。オフライン総当たり攻撃への耐性を確保するため、以下を実装する：(a) クライアント側で3回以上の連続誤入力時に指数バックオフ（3回目失敗後1秒、4回目2秒…最大30秒）による遅延時間を設定し、ロックアウト期間中は送信ボタンを非活性化する、(b) パスコード強度・文字数要件（10文字以上72文字以下、zxcvbnスコア2以上、NFR-SEC-13参照）を適用する、(c) パスコード入力成功時に失敗カウントおよびロックアウトをリセットする。FR-CRYPT-05のメモリのみ保持原則と矛盾しないよう設計する。 |
| FR-CRYPT-05 | 展開されたマスターキーはブラウザのメモリ上にのみ保持し、永続化しない（再読み込みや家族切替で消去される）。                                                                                                                                                                                                                             |
| FR-CRYPT-06 | パスコード忘却時にマスターキーを再アンラップできる「リカバリーキット（復元コード）」を発行し、QRコード付きのA4印刷用PDFとして出力・保存（ローカル保存、印刷、Google Drive保存）できる機能を提供する。 |
| FR-CRYPT-07 | リカバリーキットを用いた復元（Redeem）時は、Recovery CodeのみではMasterKeyを復号できず、登録メールアドレスへの2段階認証（Email OTP: 6桁・有効期限10分・試行回数5回制限・60秒レート制限）の成功を必須とする。 |
| FR-CRYPT-08 | リカバリーキットの再発行機能を提供する。再発行時は旧Recovery暗号情報をDBから完全上書き・破棄し、旧Recovery Codeを即座に無効化する。GUI（家族設定画面）およびPDF上に現在有効なリカバリーキットの発行日時および発行者を表示する。 |

## 6. 非機能要件

### 6.1 セキュリティ要件

| ID         | 要件                                                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-SEC-01 | 実際のパスワードそのものはシステム上いかなる場所にも保存しない（保存対象は「ヒント」に限定する設計思想）。ただしユーザーが入力する「ヒント」は暗号化されているため、運用管理者でもその「ヒント」が実際のパスワードでないかどうかの知得はできない。                   |
| NFR-SEC-02 | パスワードヒントはエンドツーエンド暗号化（E2EE）を採用し、サーバー・データベース管理者を含む何者もサーバー側で平文を閲覧できない。                                                                         |
| NFR-SEC-03 | 鍵導出関数はPBKDF2（ハッシュ関数SHA-256、反復回数30万回）を用い、対称暗号方式にはAES-GCM（256bit）を採用する。                                                                       |
| NFR-SEC-04 | 家族・レコード・ユーザーに関わるバックエンドAPIはすべて認証必須とし、未認証アクセスを拒否する。                                                                                           |
| NFR-SEC-05 | サービスレコードへのアクセスは「個人所有（ownerType: user かつ所有アカウント）」または「家族共有（ownerType: family かつ同一家族グループ）」の場合のみ許可し、削除・共有解除・管理者変更は個人所有者または家族共有レコードの管理者（admins）のみに制限する制御をサーバー側（`convex/rls.ts`）で必ず行う（クライアント側の表示制御に依存しない）。 |
| NFR-SEC-06 | URLからOGP情報を取得する機能はSSRF対策を実施する：スキームをhttp/httpsに限定、DNS解決したIPアドレスがプライベート／ループバック／リンクローカルの場合は拒否、リダイレクト追跡のたびに再検証、最大リダイレクト回数・レスポンスサイズ・タイムアウトを制限する。 |
| NFR-SEC-07 | CSV出力はスプレッドシートソフトでの数式実行につながる先頭文字をエスケープする（CSVインジェクション対策）。                                                                                    |
| NFR-SEC-08 | サーバー間内部API（Firebase UIDによるユーザー照会）は共有シークレットによるヘッダー認証で保護する。                                                                                   |
| NFR-SEC-09 | 生体認証関連の秘匿情報（WebAuthn資格情報ID、暗号化済みパスコード等）は端末ローカル（IndexedDB）にのみ保存し、サーバーへは送信しない。                                                                |
| NFR-SEC-10 | すべての入力値をスキーマバリデーション（文字数上限、Base64／IV形式の妥当性等）によりクライアント・サーバー双方でチェックする。                                                                         |
| NFR-SEC-11 | OGP取得処理は、リダイレクト追跡回数の上限設定やレスポンスサイズの検証・制限を行い、悪意あるレスポンスによるメモリ枯渇（DoS）を防止する。                                                                     |
| NFR-SEC-12 | CSP（Content Security Policy）等のセキュリティヘッダーを設定し、XSS発生時のデータ外部送信リスク（マスターキー窃取を含む）を低減する。CSP自体はXSS脆弱性の根本原因を防ぐものではないため、出力エスケープ・依存パッケージ管理・Trusted Types等の多層防御と組み合わせて運用する。 |
| NFR-SEC-13 | 家族パスコードの強度要件として最低10文字以上、および `@zxcvbn-ts` による推測耐性判定（スコア2以上）を必須とし、入力時に強度メーターによる視覚的フィードバックを提供する。                                                                                               |
| NFR-SEC-14 | 鍵導出のセキュリティ強度（PBKDF2の反復回数等）を将来引き上げる場合でも、既存ユーザーの登録データが復号できなくなることがない設計とする。                                                                     |

## 8. 主要データ項目一覧（概要）

要件レベルでの主要エンティティと項目。詳細な型・インデックス定義は設計書を参照。

- **家族グループ** ：家族名、暗号化済みマスターキー、マスターキー用IV、マスターキー導出用ソルト

## 9. 制約事項

- ログイン手段はGoogleアカウントのみであり、他の認証方式は提供しない。
- 家族パスコードは10文字以上72文字以下とする（zxcvbnの計算負荷およびDoS対策、パスワードクラック耐性確保）。
- CSVインポート／エクスポートで扱える1レコードあたりの認証情報数は、CSV列設計上、最大10件を前提としている。
- CSVインポートは1回あたり最大500行までとする（サーバー側で強制）。
- パスワードヒント・メモ等のテキスト項目には文字数上限が設けられている（メモ：10,000文字、パスワードヒント：2,000文字（登録・編集時）等）。
- 家族グループ内では非対称な権限ロール（ファミリー管理者／メンバー）を提供し、低リテラシー層によるデータ誤操作・破壊を防止する。家族グループ内には最低1名のファミリー管理者が必須となる。

## 10. 今後の検討課題（実装から推測される拡張余地）

- 多言語対応（現状UI文言は日本語に固定）
- 複数家族（マルチ・ワークスペース）対応：1ユーザーが複数の家族グループに所属し、切り替えられるようにする案。現行は1ユーザー1家族グループを前提としている（3章・4章）ため、実現する場合は前提条件・データモデルの見直しを伴う。
