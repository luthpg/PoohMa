# Pitfalls: PR レビュー・外部 AI 審査 & ガードレール

PR レビュー対応、外部 AI（CodeRabbit等）指摘の審査、および設計上の過剰防衛に関する落とし穴と回避法です。

---

### PR の経緯・レビュー文脈を確認せずにコード差分だけで独断判断する罠

- **問題**: PR 上で外部レビュアーから提案されたコミットの妥当性を評価する際、GitHub 上のディスカッション経緯（`gh pr view --comments`）を追わずに、コード差分だけで「仕様違反」と決めつけ、優れた改善を安易にロールバックしようとしてしまう。
- **回避法**: コード差分を見る前に必ず `gh pr view --comments` でレビュー指摘の意図・経緯を追跡し、開発ブランチの断面においてより堅牢な設計（断面最適）であれば前向きに採用する。

---

### 外部 AI（CodeRabbit 等）レビュー指摘の盲目的な鵜呑み（最重要注意点）

- **問題**:
  - CodeRabbit 等は、一般的な React / TypeScript の慣習に基づいて「catch した `error.message` をトーストで表示せよ」「すべての分岐で詳細例外を投げよ」といった提案を機械的に行う。
  - AI エージェントがこれを盲目的に鵜呑みにして採用すると、PoohMa の最重要不変条件（[`.ai/invariants.md`](../invariants.md) 第5節: **トーストでの生エラー直接露出禁止**）に抵触し、内部情報漏洩（CWE-209）や暗号鍵漏洩リスクを招く。
- **回避法**:
  - 外部レビュー指摘を評価する際は、**必ず [`.ai/invariants.md`](../invariants.md) と照合して安全性を審査する**。
  - PoohMa の不変条件に反する提案（生エラー露出、暗号化省略等）は、**「PoohMa の不変条件・セキュリティ原則に反するため」と明確な根拠を示して毅然と却下する**。

---

### マイグレーション完了前提の過剰なクライアントサイドガードコードの混入（KISS原則違反）

- **問題**:
  - スキーマ変更やデータ移行（例: `stableId` 追加）を行う際、「未バックフィルのレコードが存在したらクライアント操作（エクスポート等）を拒否して例外を投げる」といった過剰なガードをフロントエンド・Hooks に混入させてしまう。
  - これにより、本番環境でマイグレーションを実行するまでユーザー操作がブロックされ、運用が破綻する。
- **回避法**:
  - マイグレーションは「スキーマと関数を用意し、PR 中または本番リリース時に CLI（`npx convex run migrations:...`）から手動ワンショットで完了させる」運用とする。
  - クライアント側コードには過剰な未バックフィル検査ガードを設けず、`record.stableId || ""` のような自然なフォールバックで吸収する（KISS原則）。

### データインポート時の管理者・メンバー解決における過剰拒否

- **問題**: CSVインポート等で家族外メンバーが指定されていた際、即座に例外をスローして全体中断してしまうと、E2E シード投入やユーザーの既存インポートが破綻する。
- **回避法**: 家族外メンバーはエラー中断せずスキップし、インポート実行者および家族内実在メンバーを管理者に登録するフォールバック仕様に統一する。スキップされた旨はプレビュー UI の警告（コールアウト）でユーザーに明示する。
